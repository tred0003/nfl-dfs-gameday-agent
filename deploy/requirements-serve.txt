# Serving container only. Smaller than the training image on purpose.
#
# Absent because inference does not need them: scikit-learn, pulp, matplotlib,
# openpyxl, nfl_data_py, pyarrow (the server receives JSON, it never reads a
# parquet).
#
# SCIPY IS NOT ABSENT, AND THIS COMMENT USED TO CLAIM IT WAS. The generated lock
# from build fc99ad9 says scipy==1.17.1 sits in the image regardless: it is a
# hard dependency of xgboost itself, not something sklearn drags in. The
# reasoning below about keeping sklearn out is still right; the claim about what
# that bought was wrong, and nobody could have known it without asking the image.
# That is the difference between a requirements file and a lock.
#
# scikit-learn stays out DELIBERATELY, and it cost a failed deployment to keep
# it that way. model_io.load() originally built an xgb.XGBRegressor -- the
# sklearn-API wrapper -- whose constructor imports sklearn, so the container
# died at startup with "ImportError: sklearn needs to be installed". The fix was
# the native xgb.Booster loader, not a bigger image. Keep it that way: pulling
# sklearn in drags scipy with it, and this image is pulled on every scale-up.
#
# A serving image is pulled on every scale-up, so its size is latency. Which
# makes the other thing the lock revealed worth acting on: nvidia-nccl-cu12
# is in this image. It arrives as a dependency of the stock xgboost wheel on
# linux, it is a multi-hundred-megabyte GPU collective-communications library,
# and this container has no GPU and never will -- 4.1 already established that
# gradient-boosted trees on 51k rows are CPU work. It is pure cold-start cost.
#
# The fix is the xgboost-cpu wheel, which is the same library built without the
# NVIDIA dependencies. Not done in this commit because it changes what gets
# installed and therefore needs its own build to verify, and the image that is
# about to be registered as version 3 is already built and tested.
# NEXT REBUILD: swap xgboost for xgboost-cpu, diff the lock, compare image size.
#
# ---------------------------------------------------------------------------
# WHY THESE ARE == AND NOT >=
#
# Every line here used to say >=. That is a recipe, not a lockfile: pip resolves
# it fresh against the package index on every build, so the same Dockerfile at
# the same commit can produce a different image. Same inputs, different bytes,
# and no way to tell which build is running in front of you.
#
# It already changed a decision once. Phase 4.2 needed a SHA-tagged serving
# image and the obvious move was to rebuild. That was wrong for exactly this
# reason, and the image got retagged instead -- one digest, two tags, provably
# the artifact that was tested. Retagging only works while the code is
# unchanged. The moment it changes you must rebuild, and then a floating
# requirement means the new image differs from the old one in ways you did not
# author and cannot enumerate.
#
# WHERE THE NUMBERS COME FROM. Not from "latest that works" -- from the
# environment the ARTIFACT WAS TRAINED IN. models/current/model_card.json
# records python 3.11.15, xgboost 3.2.0, pandas 3.0.5, and model_io.load()
# already warns at startup when the serving xgboost does not match the card.
# Pinning to the card's versions makes that warning structurally impossible
# rather than merely unlikely, and it means a prediction that differs between
# this container and the laptop is attributable to the platform instead of to
# package drift. That distinction is the entire value of the 0.6419-vs-0.6423
# check from phase 4.1, applied to serving instead of training.
#
# WHAT THIS IS NOT. Six == lines are not a lock. Transitive dependencies still
# float: Flask pulls werkzeug, jinja2, itsdangerous, click and blinker;
# google-cloud-storage pulls google-auth, google-api-core, protobuf and more.
# A werkzeug release has broken a pinned Flask before. The real fix is a
# generated lock, which is why cloudbuild.serve.yaml now emits `pip freeze` as
# a build artifact -- promote that file to a constraints file and this becomes
# reproducible all the way down.
# ---------------------------------------------------------------------------

# The numeric path. These three decide what number comes back, so they are
# pinned hardest and are the ones the model card knows about.
xgboost==3.2.0               # matches model_card.json; .ubj is forward-compatible, but "compatible" is not "identical"
pandas==3.0.5                # matches model_card.json
numpy==2.4.6                 # pandas/xgboost both build on it; floating it floats them

# The transport path. These decide whether a request arrives and a response
# leaves. They cannot change a prediction, only whether you get one.
Flask==3.1.3
google-cloud-storage==3.13.0   # model_io pulls the artifact from AIP_STORAGE_URI

# The production WSGI server; Flask's own is single-threaded and not one. This
# was the one line left floating when the file was first pinned, because
# gunicorn does not install on Windows and there was no local environment to
# source a truthful version from -- guessing one would have defeated the point.
#
# 26.2.0 is not a guess. It is what build fc99ad9 actually resolved, read back
# out of the lock that build emitted. The image was not rebuilt to adopt it:
# this line now describes bytes that were already there.
gunicorn==26.2.0
